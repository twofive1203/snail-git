# 开源门槛：可公开、可信任、不扩功能

> **未实现/待办。** 对应计划是 `docs/plans/2026-10-27-001-feat-oss-readiness-plan.md`，复选框都未勾。本文是需求，不是已完成记录。

## Problem Frame

SnailGit 已经能满足作者自己的日常 Git 操作，但还不能诚实地公开。仓库没有 `LICENSE`，`package.json` 仍是 `"private": true`，README 自称开源，打包却只有 Windows NSIS。外人打开仓库时，无法判断能不能用、能不能改、支持哪些系统，也不知道危险操作实际会跑什么 git 命令。

这次只补“可以公开”的门槛。不借开源之机补 blame、交互式 rebase、跨平台安装包或性能重构。

---

## Actors

- A1. 第一次打开仓库的访客：用 1 分钟判断协议、平台和这个工具不是又一个 GitHub 客户端。
- A2. 现有 Windows 用户：在丢弃改动、改写历史或删除引用前，能核对并取消即将执行的命令。
- A3. 贡献者：按文档在 Windows 上装起来、跑现有检查，并用中文或英文提问题。

---

## Key Flows

- F1. 判断能不能用
  - **Trigger:** 访客打开 README 或仓库根目录。
  - **Actors:** A1
  - **Steps:** 看到 MIT 与 `LICENSE`；看到英文导语和中文正文；看到仅 Windows 已验证；看到真实界面截图；看到日志是分页加载并有上限，而不是“大仓库也丝滑”。
  - **Outcome:** 访客知道可以按 MIT 使用和修改，也知道 Linux/macOS 还不能当正式平台。
  - **Covered by:** R1, R2, R3, R4, R5
- F2. 危险操作前核对命令
  - **Trigger:** 用户发起会丢弃未提交改动、删除引用或改写历史的操作。
  - **Actors:** A2
  - **Steps:** 弹出现有风格的确认框；框内用等宽字体展示即将执行的命令，并可复制；取消、Esc 或点遮罩后不执行任何写操作；确认后才执行，且实际参数与展示一致。
  - **Outcome:** 用户能在终端复现同一次操作，也能在执行前退出。
  - **Covered by:** R6, R7, R8, R9

## Requirements

**公开身份**

- R1. 仓库根目录提供 MIT `LICENSE`。README 和界面关于信息必须与该协议一致，不得再写没有协议支撑的“开源”。
- R2. 这是桌面应用，不是 npm 库。保持 `package.json` 的 `"private": true`，避免误发布到 npm。公开源码不等于发布 npm 包。
- R3. README 顶部增加一段英文导语，说明它是轻量 IDEA 风格 Git 客户端、MIT、仅 Windows 已验证。正文保持现有中文，不整篇改写成英文。
- R4. README 明确：当前只提供已在 Windows 上验证的 NSIS 安装包；Linux 和 macOS 未支持、欢迎贡献。不得新增这些平台的打包目标，也不得展示对应下载入口。
- R5. README 至少放 3 张从真实 Windows 应用截取的图：日志拓扑、提交与双栏 diff、Shelf 或三方合并之一。禁止用生成图或浏览器 mock 冒充。暂时截不到时，必须标明“截图待补”，不能假装已经有。

**危险操作可核对**

- R6. 以下操作在执行前必须经过一次确认，并展示可复制的真实命令。已有确认框的，只补命令，不再套第二层确认：
  - 重置到某提交（当前会直接 `reset --mixed`，必须补上确认）
  - 丢弃工作区或已暂存改动，以及代码块回滚
  - 删除未跟踪文件
  - 删除本地分支，含强制删除
  - 删除远程分支
  - 强制推送（只允许 `--force-with-lease`，展示文本也不得出现裸 `--force`）
  - 删除远程、删除远程标签
  - 压缩提交
  - 中止进行中的合并、变基、挑拣或还原
  - 丢弃贮藏
- R7. 复制出的文本必须能在终端复现同一次操作。多步操作按实际顺序逐条列出。确认框里的命令和随后执行的参数必须一致。
- R8. 取消、Esc 或点遮罩都不改仓库。
- R9. 日常操作不新增这层确认：提交、amend、普通推送、fetch、pull、检出、挑拣、还原提交、开始合并或变基、新建分支或标签、创建或恢复 Shelf、从应用列表移除仓库。

**能力边界写清楚**

- R10. README 写明日志每页 200 条，继续加载最多到 2 万条，之后停止并沿用现有上限提示。不得把“1 万条 60fps”或大仓库丝滑写成已实现能力。
- R11. 这次不改变日志分页、加载上限和整页渲染行为。
- R12. 贡献说明写清 Windows 下的启动方式，以及现有 `typecheck`、`lint`、`test:rust` 怎么跑。问题和拉取请求接受中文或英文。
- R13. 公开仓库需要有一个 Windows 自动化检查，覆盖 R12 里的现有检查命令。不要求发布流水线，也不要求 Linux/macOS 检查。

## Acceptance Examples

- AE1. **Covers R6, R7, R8.** 用户在日志里选择“重置到此提交”。确认框出现可复制的 `reset --mixed` 命令；取消后 `HEAD` 和工作区不变；确认后执行的就是所展示的 mixed reset，不是 hard reset。
- AE2. **Covers R6, R7.** 用户打开强制推送。确认或推送预览中的命令含 `--force-with-lease`，且整段文本不包含可被误读成裸 `--force` 的参数。实际推送也不使用裸 `--force`。
- AE3. **Covers R4, R5, R10.** README 不出现 Linux/macOS 下载按钮，不把 mock 图写成产品截图，并写明 200 条分页和 2 万条上限。

## Success Criteria

- 访客不读源码也能回答：MIT、仅 Windows 已验证、日志有分页上限、危险写操作前能看到命令。
- 现有提交、拉取、检出等日常路径不比现在多一次确认。
- 实现者不用猜测协议、平台承诺、哪些操作算危险，以及这次是否要做虚拟滚动。

---

## Scope Boundaries

- 不补文件历史、blame、行级暂存、交互式 rebase、图片 diff、语法高亮、浅色主题、worktree、子模块、LFS、提交签名。
- 不把 SnailGit 做成 GitHub/GitLab 登录或 PR 客户端。
- 不做成基于 IntelliJ 运行时的重型 Git 客户端，不引入插件系统。
- 不新增 Linux/macOS 打包目标，不承诺三平台可用。
- 不做日志虚拟滚动，不改 200 条页大小和 2 万条上限。
- 不发布 npm 包，不在未获确认时创建 GitHub 仓库、打 Release 或上传安装包。
- 不把 Shelf 删除伪装成 git 命令；它不在 R6 的命令展示范围内。
- 自动更新、代码签名、winget 不在这次范围。

---

## Key Decisions

- MIT：采纳门槛最低，允许商业使用和再分发，只保留版权声明。
- 第一次公开只发已验证的 Windows：当前只有 NSIS 目标，macOS 无法在本机验证。未验证的包比“尚未支持”更伤信任。
- 命令只在危险操作前展示：日常操作不加面板或状态栏日志。
- 大仓库只写清上限：虚拟滚动会改拓扑图，超出“先不扩功能”。
- 保留 `"private": true`：纠正调研时“去掉 private 才算开源”的说法。开源看协议和公开源码，不看 npm 发布标志。
- README 英文导语加中文正文：现有文档是中文；英文导语只解决访客第一眼看不懂的问题。

## Dependencies / Assumptions

- 截图必须来自本机运行的 Windows 应用。实现时如果无法启动界面，只能留下“截图待补”，不能生成替代图。
- 现有确认框可以扩展出命令展示；重置到提交目前没有确认，这是已核对的缺口。
- 强制推送目前只走 `--force-with-lease`。这次只要求展示与执行一致，不改变该安全约束。
- 真正把仓库设为公开、打 Release，是另一次需要确认的外部操作。
